Ideation: testing the tuner's audio input without the laptop, speakers or a quiet room

Date
2026-10-17
Topic
headless-audio-input
Mode
repo-grounded

Focus: testing the audio input means giving up the laptop to play tones and record analytics, or keeping a room quiet, which is close to impossible with a newborn. Can the tuner read from a virtual audio input so these checks run headless?

Short answer

Yes. Since stage 1 merged (PR #5, 16fd1d2), the app reaches the microphone through one call: CaptureCreate(capturePush, context, &capture) at swift/AppDelegate.swift:603. Anything that calls the same CapturePush callback with float samples looks like a microphone to the engine. A file or tone source behind that call is a virtual input with no driver, no mic permission and no sound in the room. A loopback driver such as BlackHole still has a use, but only for checking the real CoreAudio path by hand.

Grounding Context

Codebase Context

  • Capture today. Sources/TunerCapture/CaptureHAL.m:192-202 opens only the system default input (kAudioHardwarePropertyDefaultInputDevice). There is no device picker and no UID lookup, and it asks the device for 44100 Hz. The callback hands samples to the engine through typedef void (*CapturePush)(void *context, const float *samples, int count) (TunerCapture.h:65).
  • Engine. A plain C core with no globals, running on its own thread. It reads 1024-sample hops from a ring of 32768 floats that drops whole blocks on overflow, and publishes a per-hop snapshot (found, note, cents, frequency, reference, count). Engine.swift exposes push, start(onHop:) and acquire(). TunerEngineAcquire allows only one consumer.
  • Tests. make test runs in CI and replays 28 golden fixtures (raw float32 .bin plus .header) produced by a frozen copy of the old Audio.m. The fixtures cover sines, harmonic stacks, white noise and silence. The plan's rule is "Tests never open an audio device" (plan:909). Everything that needs hardware is on a manual checklist on the owner's Mac.
  • Gaps. No fixture mixes noise with a tone, starts from silence, or uses a real instrument. No per-hop results are logged or exported anywhere. The only export is the "c" key, which copies one line. The test helpers that turn a file into per-hop records (CoreRunner.swift, RunningEngine.swift) live only in the test target.
  • How checks run now. Sine WAVs go through the speakers with afplay into the built-in mic, with window captures and CGEvent clicks. One run failed because AirPods were the default input and output. The owner runs measurement commands on the running app themselves.
  • What comes next. Stage 2 replaces CaptureHAL.m with AVAudioEngine and follows the default device (plan KTD8, U9). Anything built at the CapturePush level, or above it in the app, carries over.
  • Project boundaries. STRATEGY.md rules out work on the Linux port and code signing for now.

Past learnings

docs/solutions/ui-bugs/appkit-views-draw-at-window-size-from-dirtyrect.md is about drawing, not audio. It is a reminder that some bugs only show in the running app.

External context

  • BlackHole (GPL-3, brew install blackhole-2ch) is the usual macOS loopback driver. libASPL (MIT) can build a virtual input that generates a tone inside coreaudiod. Apple's TN2091 shows how to pick an input by UID (kAudioHardwarePropertyTranslateUIDToDevice, then kAudioOutputUnitProperty_CurrentDevice).
  • GitHub's macOS runners sometimes have no audio device. One report puts it at about 30% of runs (runner-images #13668). Microphone permission prompts have hung CI before (#9330). A virtual device probably still needs the mic grant. So CI should feed samples in software, not through a device.
  • Pitch-detector test suites (aubio, sevagh/pitch-detection) use generated sines, silence cases, real instrument clips and degraded audio. mir_eval scores the share of frames within 50 cents.
  • Sample sources: the University of Iowa instrument samples ("without restrictions") and NSynth (CC BY 4.0). MDB-stem-synth is non-commercial only.

Idea 1

1. A file or tone input for the real app, chosen at launch

Rank 1Axis: Where samples enterConfidence 85%Complexity Medium
Description
Add an input-source setting that the app resolves before it calls CaptureCreate. file:take.wav or tone:440 starts a small feeder thread. It pushes 1024-sample blocks through the same CapturePush callback, paced at real time, and reports its own sample rate. The setting is a UserDefaults key, so it works straight from the shell: open Tuner.app --args -InputSource file:take.wav. The whole app runs (window, strobe, meter, readout) and the microphone is never opened.
Axis
Where samples enter
Basis
  • direct: swift/AppDelegate.swift:603 let status = CaptureCreate(capturePush, context, &capture), and the engine is built from CaptureSampleRate(capture) at :613. One call site, one rate source.
  • direct: TunerCapture.h:65 typedef void (*CapturePush)(void *context, const float *samples, int count).
  • direct: Sources/GoldenReference/main.m:64-68 already feeds canned 1024-frame blocks to the old capture code, so blocks from a file are a proven way in.
  • external: Cocoa's argument domain lets -Key value on the command line override UserDefaults. Voice-pipeline CI paces replay at real frame duration.
Rationale
This is the "virtual audio input" asked for, built in software. There is no driver to install, no mic prompt, no speakers and no room noise, and the owner can keep working while it plays. Pacing at real time keeps the ring, the hop thread and the 20 ms redraw timer running as they do live. The existing window-capture and click scripts then work on silent, repeatable input.
Downsides
It does not test CaptureHAL.m itself; idea 6 covers that. It needs a WAV reader (ExtAudioFile is the easy choice), and files at another rate must either be resampled or passed through as that rate. Stage 2 replaces CaptureHAL.m, so the selector belongs in the app layer, not inside the HAL file. Launching the app on the owner's Mac still needs the owner's go-ahead each time.

Idea 2

2. tuner-run: sound file in, one line of numbers per hop out

Rank 2Axis: Observing resultsConfidence 85%Complexity Low–Medium
Description
A small command-line tool on the engine, with no AppKit. It takes a WAV or a tone spec plus the app's settings (reference, temperament, key, filter, downsample, note filter). It writes one JSON line per hop: time, found, note, cents, frequency, reference, count, overruns. The default mode runs faster than real time through TunerEngineProcessBlock for CI. A paced mode goes through the ring and thread. "Record analytics" becomes tuner-run cello.wav > cello.jsonl, and it runs over SSH, in CI or from an agent, with no window.
Axis
Observing results
Basis
  • direct: TunerCore.h:150 TunerEngineProcessBlock processes a block "on the caller's thread … bypassing the ring". TunerSnapshot (TunerCore.h:80-98) already holds found, note, deviation, frequency and count.
  • direct: Tests/TunerCoreTests/Support/CoreRunner.swift:81 (runCore) and RunningEngine.swift:18-20 already turn input into per-hop records, but only inside the test target.
  • direct: the evidence scan found no per-hop logging, CSV or JSON export anywhere. The plan's measure target (plan:874) is not built.
Rationale
Most of the code already exists as test scaffolding, so this mostly moves it into a product. Once one log format exists, the scorecard (idea 5), recorded takes (idea 3) and the noise sweep (idea 4) can all use it. A good first step: it changes no capture code and can merge on its own.
Downsides
The fast mode skips the ring and thread, so it can't see dropped blocks; that needs paced mode. If the live app should also write the log, it has to be the engine's single consumer, so the display and the log share one acquire loop. It needs the same WAV reader as idea 1.

Idea 3

3. Record a real sound once, replay it forever

Rank 3Axis: Observing resultsConfidence 70%Complexity Medium
Description
The app keeps the last 30–60 seconds of raw input in a preallocated side ring, about 5–10 MB at 44.1 kHz. A key next to "c" dumps it as a .bin and .header in the existing fixture format, plus the hop log from idea 2. The header also records device name, sample rate and build commit. Any time the room happens to be usable, or a real instrument reads oddly, one keypress turns that moment into a file that ideas 1 and 2 can replay on any Mac. Each take can start with a short leader, two seconds of silence and then an exact 440 Hz tone, so a replay can confirm the file's sample rate is labelled right before trusting it.
Axis
Observing results
Basis
  • direct: the evidence scan records "no recording of the input stream to disk" in either tree. The "c" key (TunerView.swift:86-102) copies one line.
  • direct: Tests/TunerCoreTests/Fixtures/README.md defines NAME.bin as float32 hops of 1024 samples plus a .header with rate and hops.
  • direct: plan KTD4: the audio callback does "nothing else, no allocation, no lock, no log". The tee therefore has to be a copy into a preallocated ring that another thread writes out.
  • external: QEMU record/replay logs only the non-deterministic inputs, audio included, and replays the rest exactly.
Rationale
Real-sound testing needs a quiet room and the laptop for minutes, not sessions. After that the recording does the work. It also catches problems the way they actually show up: someone notices something odd mid-use.
Downsides
Raw household audio must stay out of the public repo, so takes live in a local folder with a hash manifest. Real clips can't be judged against the frozen old engine: the fixture screen shows found, note and count flipping between builds on threshold cases, and the old engine has known undefined behaviour. Judge them with idea 5's scorecard, or by eye once.

Idea 4

4. The house as a test signal: tones mixed into recorded household noise

Rank 4Axis: Test signalsConfidence 70%Complexity Low–Medium
Description
Record about a minute each of the real house, once, on any recorder: the white-noise machine, HVAC, kitchen, TV, the baby. Keep them local. A generator adds known tones and harmonic stacks to each bed at set signal-to-noise steps (+30 down to −10 dB). Because the tone is added in software, the right answer is exact. The output is a table: per pitch, the lowest SNR where the tuner still finds the note within 5 cents, and how often each bed alone produces a false note. The pitched sounds (a cry, speech, a kettle) show whether the tuner locks onto things that aren't instruments.
Axis
Test signals
Basis
  • direct: the evidence scan: "No fixture mixes noise with a tone". The only noise fixture is white noise, --noise 0.5:12345 (Scripts/fixtures.sh:58-60), and GoldenTests.swift:115-125 checks only that noise alone is never found.
  • direct: plan:224 defers "A noise gate for quiet instruments in noisy rooms".
  • external: the Audio Degradation Toolbox mixes noise into clean audio for this kind of test. mir_eval scores the share of frames within tolerance.
Rationale
The obstacle becomes the test data. "Does it work in our house?" gets an answer at any hour on any machine. The deferred noise-gate decision gets a number to rest on instead of a guess.
Downsides
The tuner has no way to tell a voice from an instrument, so a cry that reads as a note is expected behaviour, not a bug. Treat the false-note rate as a measurement, not a pass/fail gate. Recording the beds uses idea 3's recorder or a phone. The beds hold family audio, so they stay out of git.

Idea 5

5. A tuner scorecard on scenes with a known answer

Rank 5Axis: Test signalsConfidence 65%Complexity Medium
Description
Extend the fixture generator from static tones to short scenes where the right answer is known: silence then a note, a note that fades, a steady note at a set detune, and a note under noise at a set SNR. A small scorer reads idea 2's hop log and prints a few numbers per scene: share of hops within 5 cents, worst cents error after settling, hops from onset to first found, and false finds in silence. The owner gets the analytics as a table they can diff between builds, instead of watching the strobe.
Axis
Test signals
Basis
  • direct: the evidence scan: "No fixture starts from silence and then produces a tone" and "no envelope, attack, decay, or onset". Headers already carry static truth keys, expect_hz and expect_cents.
  • direct: Tolerance.swift skips the first 20 hops of every fixture as warm-up, so onset behaviour is never checked today.
  • direct: plan:198 sets a latency target ("about 23 ms") and plan:177 says "Silence is never mistaken for a quiet room". Neither is measured automatically.
  • external: mir_eval's raw pitch accuracy and aubio's sine-plus-silence tests.
Rationale
The goldens prove the new engine matches the old one. They can't say whether either is right on a plucked note. They also stop applying once stage 2 changes sample rates. A scorecard based on known answers keeps working across engine changes.
Downsides
Keep it small. Per-commit trend dashboards and a second pitch detector as referee are more than a one-person project will read. Glides and vibrato have no clean per-hop answer, because the engine measures over a 16384-sample window, so leave them out.

Idea 6

6. Pick the input device by UID, for a silent manual check through BlackHole

Rank 6Axis: Where and when checks runConfidence 60%Complexity Low
Description
Add device:<uid> as a third value of idea 1's setting. Capture translates the UID to a device and binds to it instead of the default. At startup it logs one line: "capturing from <name> <uid> @ <rate>". With BlackHole 2ch installed, a small player writes test tones to BlackHole's output and the tuner reads BlackHole's input. The real CoreAudio capture path runs with nothing audible and the owner's default devices left alone. This is a manual check the owner starts. It is not part of make test.
Axis
Where and when checks run
Basis
  • direct: CaptureHAL.m:192-202 // Get the default input device … return kCaptureStatusNoInputDevice;. No UID or device-list code exists in either tree.
  • direct: memory note: "the first run with AirPods connected played the tone into the AirPods and captured from their mic, so nothing registered".
  • external: TN2091 (UID to device, then kAudioOutputUnitProperty_CurrentDevice). BlackHole is GPL-3, the same licence family as this repo.
Rationale
Ideas 1–5 never touch CaptureHAL.m. This is the cheapest way to check that path without speakers or a quiet room. The startup line also makes a wrong-device run obvious, which would have caught the AirPods failure straight away.
Downsides
afplay can't choose an output device, so the player has to be sox, ffmpeg or a few lines of Swift. The mic permission grant probably still applies. Not for CI: hosted macOS runners sometimes have no audio device. Stage 2 replaces the HAL code, so the UID lookup has to be redone there.

Works today with no code

Install BlackHole and set it as both the default input and the default output. Then play tones with afplay and start Tuner. The laptop stays silent. The catch: every system sound and call goes into BlackHole too, and the defaults have to be put back afterwards. Idea 6 removes that catch.
